# Stage 3C-E: confirmatory runner and analysis engineering

Status: engineering implementation only. This stage creates no formal Stage 3C
run, scientific result, or Mechanism decision. The frozen scientific protocol
remains `docs/STAGE3C_CONFIRMATORY_PREREGISTRATION.md` at commit
`63d51ffe10a40515d4e4f208746019ec3da3ad82`.

## Modules and entry points

`src/scalar_baseline/stage3c.py` owns strict configuration, horizon-stable
random schedules, Stage 3B class reuse, offline measurements, atomic run
publication, artifact validation, gates, engineering audits, and resource
limits. `src/scalar_baseline/stage3c_analysis.py` owns the frozen paired analysis
and decision. No Stage 3A or Stage 3B source is modified.

The command entry points are:

- `scripts/run_stage3c.py dry-run`: validate the 40 configurations and schedule
  prefixes without initialising a simulation or creating formal output;
- `scripts/run_stage3c.py first-pair`: run only seed `2026092101`, B0 then C,
  and produce an outcome-blind engineering receipt;
- `scripts/run_stage3c.py remaining`: refuse execution until the first-pair
  receipt and both arm hashes validate, then run seeds `2026092102-2026092120`
  in ascending order, B0 then C;
- `scripts/run_stage3c.py analyse`: refuse execution until all 40 immutable runs
  pass validation, then execute the frozen analysis once;
- `scripts/audit_stage3c.py`: generate machine-readable configuration,
  schedule-prefix, pair-identity, B0-replay, single-change, isolation, cargo,
  and static-resource audits;
- `scripts/summarise_stage3c.py`: a dedicated entry point to the same gated
  analysis function.

Stage 3C-E must call none of the execution modes except `dry-run`. The next
permitted step is a separately authorised Stage 3C-R first pair.

## Frozen simulation reuse and randomness

`Stage3CB0Simulation` inherits `PairedB0Simulation` and
`Stage3CRecoverySimulation` inherits `RecoverySimulation`. Neither Stage 3C
class defines `_move`, `_contacts`, or any recovery method. The only simulation
engineering change is replacement of precomputed random arrays with
horizon-stable arrays.

For every ant, the first 12,000 FCRW turns are generated by the exact Stage 3B
procedure and seed stream. The 6,000-step extension uses fixed independent sign
and magnitude streams, with the first extension sign conditioned on the final
Stage 3B sign under the same FCRW repeat probability. Initial heading, follower
noise, and recovery side retain their existing independent streams. Therefore
the 12,000-step arrays are byte-for-byte prefixes of the 18,000-step arrays, B0
and C share all treatment-independent inputs, B0 never reads recovery sides for
movement, and C reads them only when entering the frozen recovery branch.

## Formal directory and atomic publication

Future formal evidence uses this structure:

```text
results/stage3c_confirmatory_recovery/
  first_pair_engineering_receipt.json
  runs/<seed>/B0/
  runs/<seed>/C/
  paired_primary.csv
  confirmatory_analysis.json
```

An arm first writes to a hidden sibling temporary directory. It produces
configuration, summary, 100-step series, ledger events, field snapshots,
source identity, resources, integrity, storage, and a completed receipt; C also
produces recovery episodes. The completed receipt hashes every other file
recursively. Only a fully validated directory is atomically renamed to its
final path.

An existing completed directory is hash-validated and may be reused, never
overwritten. A failed or incomplete directory is preserved with an
`incomplete` name and blocks automatic retry. Repair or rerun requires a
documented engineering cause and separate master decision. Scientific outcome
is never a rerun reason.

Before the first formal arm, the runner records path, size, and SHA-256 for all
pre-existing Stage 1/2/2B/2C/3A/3B results, proposal/template/briefing/similarity
materials, reports, `from_prof`, and the five protected untracked trees. The
first-pair, remaining, and analyse gates all revalidate this manifest. The
manifest excludes the new Stage 3C formal directory itself.

The first-pair mode also runs and freezes an outcome-blind pre-run engineering
audit before it constructs a formal simulation. That audit binds the current
source hashes and must pass configuration, schedule-prefix, pair-identity,
Stage 3B B0 replay, single-change, navigation-isolation, cargo-classification,
and static-resource checks. Remaining and analyse modes reject a changed source
or missing audit.

## Pair, identity, and navigation validation

Pair validation removes only `arm` and `recovery_duration` before comparing B0
and C configuration records. Initial agents, field, FCRW turns, follower noise,
recovery sides, relocation, and every shared simulation parameter must match.
The machine-readable single-change audit verifies that Stage 3C adds no movement
override and that the inherited Stage 3B recovery branch remains the only
behavioural difference.

The navigation audit examines the inherited recovery movement source for food
or nest coordinates, cell direction, global gradient, field scan, source
identity, or future information. Old-food and obsolete-trail geometry is
computed only after movement for offline measurement and never enters movement
or random-number consumption. Per-run validation checks population, bounds,
finite values, cargo conservation, source classification, 24-step recovery,
artifact completeness, and recursive hashes.

## Endpoint and secondary measurements

The primary endpoint includes food B deliveries at `t=6000-17999`. A delivery
at `t=18000` lies outside the frozen observation window and is a valid
non-delivery for the endpoint. Missing food B delivery receives `12,000`.
Carried food A remains A after relocation.

Offline secondary output includes first B discovery, cumulative B deliveries,
non-delivery, old-A dwell, obsolete-trail ant occupancy, obsolete-trail scalar
mass and cells above each signal threshold, recovery outcomes, same-ant B events
within 100 steps after recovery, and pre-relocation A deliveries. These fields
are excluded from the decision function.

## Frozen bootstrap and decision

The analysis requires exactly one row for every seed `2026092101-2026092120`.
It rejects missing, duplicate, additional, replaced, non-finite, or internally
inconsistent rows as INCONCLUSIVE.

The paired bootstrap uses `numpy.random.default_rng(2026092199)` and exactly
10,000 index matrices of shape `(20,)`; each selected index carries its B0/C
pair. The statistic is mean `C-B0`. The interval is exactly:

```python
numpy.percentile(replicate_means, [2.5, 97.5], method="linear")
```

PASS requires mean C at most 80% of mean B0, bootstrap upper endpoint strictly
below zero, total pre-A delivery ratio at least 0.80, and all 40 runs valid.
Complete evidence missing any threshold is FAIL. Invalid or incomplete evidence,
an undefined baseline denominator, or an uncomputable analysis is INCONCLUSIVE.
A valid capped non-delivery participates in PASS/FAIL.

## Resource checks

Each run is limited to 600 seconds wall time, 600 seconds CPU, 2 GiB peak RSS,
512 MB temporary output, and 50 MB per retained file. The whole study is limited
to 8 CPU hours and 8 GB retained output. Boundary values are allowed; exceeding
any value stops execution and blocks continuation.

Stage 3C-E uses the committed Stage 3B resource record only for a horizon- and
run-count-scaled static estimate. It is not an 18,000-step Stage 3C measurement.
No formal seed is run to obtain an estimate.

## Test scope and evidence boundary

`tests/test_stage3c_confirmation.py` uses temporary directories, non-formal
fixture seeds, or synthetic 20-row tables. It covers the seed set and timeline,
configuration rejection, horizon-stable randomness, Stage 3B B0 replay,
unchanged 24-step recovery, pair identity, isolation, food-source
classification, endpoints, atomic publication and overwrite refusal, incomplete
evidence, execution gates, exact bootstrap, decision boundaries, resource
limits, and absence of the formal results directory.

Passing tests, audits, or fixture runs is engineering evidence only. Stage 3C-E
does not create `results/stage3c_confirmatory_recovery/`, run a confirmatory
seed, inspect a confirmatory outcome, or form a scientific conclusion.
