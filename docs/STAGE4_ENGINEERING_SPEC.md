# Stage 4A1 engineering specification and resource gate

Status: engineering only. The formal runner is `run_benchmark` in `stage4_search.py`, guarded by a distinct Stage 4B master authorisation record, a resource adjustment approval, frozen source identity, and a configured provider object. The Stage 4A1 CLI exposes only `dry-run`; it cannot launch formal simulations or API calls.

## Evidence and checkpointing

Every evaluation key includes canonical candidate, seed, full simulation configuration, and frozen source identity. A cached evaluation is reused only after its completed receipt verifies recursive file coverage, byte counts, SHA-256, and expected identity. An interrupted temporary evaluation blocks reuse until reviewed. Campaign ledgers record all opportunities, including invalid LLM proposals and duplicate candidates. A pending opportunity is completed from its recorded candidate on resume, without consuming another opportunity. At full budget the minimum-score winner is written before any held-out evaluation. Each completed campaign and the full benchmark have completed receipts covering recursive artifacts. Pre-run and post-run source identity include HEAD, tracked cleanliness, runtime, and source-file hashes. The protected snapshot recursively hashes all pre-Stage-4 result directories and supplied/report directories and files; any change blocks execution.

The validated simulation is unchanged except that the finite recovery class accepts a duration of 12, 24, 36, or 48 steps. Its four six-step local heading segments are reused; durations beyond 24 retain the fourth local heading. The zero-duration branch uses B0. The maximum local worker count is two. The LLM contract is a structured JSON provider interface and a mock only. Real provider integration, API parameters, key environment variable, and cost controls remain a Stage 4B gate. No key is written to a file.

## Historical endpoint viability audit

All 80 Stage 3C/3D `ledger_events.json` files were checked against each run's completed receipt, byte count, and SHA-256 before read-only recomputation. The zero-reference counts by exponential B0/C and hard-cutoff B0/C are 12/11/9/8. All 40 now have `tau_rec=12000` and non-recovery; all positive-reference results equal the original Equation (2) computation. Amended capped counts are 16/15/17/15, total 63/80 = 78.75%. Exponential B0 median is 12000, the 20% target is 9600, and the earliest possible recovery time is 600. Thus the target is mathematically reachable. The high capped fraction limits discrimination; ties use only the preregistered first-opportunity rule. These historical calculations do not change Stage 3C/3D decisions or constitute a Stage 4 result.

## Resource estimate from 80 completed 18,000-step Stage 3C/3D runs

The measured Stage 3C mean wall time was 33.67 seconds per run (maximum 42.97); Stage 3D mean was 32.52 seconds (maximum 47.16). Maximum measured peak RSS was 0.73 GiB per run. Mean retained data were about 3.10 MB per run, while the largest run retained 9.07 MB. The formal uncached count is 900 candidate-development runs, at most 150 winner-held-out runs, and 15 baseline development/held-out runs: **1065 runs**. These are an upper count of unique candidate-seed evaluations; cache hits leave all 180 opportunities intact.

At the combined measured mean CPU time of about 32.32 seconds, uncached CPU demand is about 9.6 hours. The combined mean wall time is about 33.09 seconds; two isolated local workers give an ideal wall time about 4.9 hours. A conservative maximum-observed-time calculation with 20% scheduling overhead is about **8.4 hours**. One worker would exceed 12 hours under that conservative calculation, so formal execution must use two workers or obtain another resource adjustment. Mean-size storage is about 3.3 GB. A conservative maximum-observed-size bound is about **9.7 GB (9.0 GiB)**. With a hypothetical 5% verified cache reuse it remains about 8.5 GiB; no duplicate rate is guaranteed because floating candidates can be unique. Peak observed RSS is below 0.73 GiB per worker, below the 2 GiB single-worker limit. This Mac reports 10 logical CPUs, 16 GiB RAM, and about 549 GiB free disk, so the two-worker compute estimate fits the local machine. AutoDL is not needed for compute alone, but the benchmark's separate 8 GiB new-storage gate still applies.

The conservative storage bound exceeds the 8 GiB limit. **Stage 4B is paused until master approves a resource adjustment** such as a larger storage allowance or a measured, lossless retention plan. The comparison budget cannot be reduced for only one method. If actual Stage 4 cache reuse or smaller artifacts later support a lower estimate, the revised resource evidence must be documented before formal execution.
